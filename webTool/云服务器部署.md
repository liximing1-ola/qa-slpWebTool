## 零、正式上线方案（Higress 网关）

> ✅ 2026-10 已上线：**https://114.55.3.96/web2026/**
> 本节是生产实际采用方案。前文「nginx 反向代理」方案适用于独立服务器；本服务器是 K8s 节点，80/443 被 Istio/Higress 网关占用，故采用本节方案。

### 0.1 架构

```
浏览器 https://114.55.3.96/web2026/
  → Higress 网关 (istio-envoy)
  → Ingress: higress-system/web2026-route  (path /web2026/)
  → Service web2026-svc:9090  → Endpoints 192.168.1.27:9090
  → 192.168.1.27 上的 gunicorn (systemd 守护)
  → MySQL
```

### 0.2 机器分工

| 机器 | 角色 | 职责 |
|------|------|------|
| `192.168.1.27`（slp-dev-sys-003） | 后端节点 | 跑 gunicorn（systemd），监听 `0.0.0.0:9090` |
| `192.168.1.23`（slp-dev，master） | 网关管理 | `kubectl apply` 加/改 Higress 路由 |

### 0.3 首次部署（两处各执行一次）

**① 后端节点 `192.168.1.27`：systemd 守护 gunicorn**

```bash
cp /opt/web2026/qa-slpWebTool/webTool/deploy/web2026.service /etc/systemd/system/web2026.service
systemctl daemon-reload
systemctl enable --now web2026
curl -I http://127.0.0.1:9090/web2026/     # 期望 200 OK
```

**② master `192.168.1.23`：加 Higress 路由**

```bash
kubectl apply -f /opt/web2026/qa-slpWebTool/webTool/deploy/k8s-web2026-route.yaml
kubectl get ingress web2026-route -n higress-system
kubectl get endpoints web2026-svc -n higress-system
```

### 0.4 日常更新代码（最常用）

在 **`192.168.1.27`** 上执行：

```bash
cd /opt/web2026/qa-slpWebTool/webTool
./update.sh                    # 一键：拉代码 -> 装依赖(如有变更) -> 重启 -> 健康检查
```

`update.sh` 常用参数：

| 命令 | 作用 |
|------|------|
| `./update.sh` | 正常更新；代码无变更时自动跳过重启 |
| `./update.sh -f` | 强制重启（代码没变也重启）|
| `./update.sh -n` | 只拉代码，不重启 |
| `./update.sh -r` | 回滚到上一次更新前的提交并重启 |
| `./update.sh -r <hash>` | 回滚到指定提交并重启 |
| `./update.sh -h` | 查看用法 |

首次拉取后需赋可执行权限：`chmod +x update.sh`。

> 若报 `无法访问远端仓库` / `Empty reply from server`，说明服务器连不上 GitHub（与分支分叉无关），按 **6.7** 用 bundle 方式更新。

等价的手工命令（脚本出问题时的兜底）：

```bash
cd /opt/web2026/qa-slpWebTool/webTool
git pull                      # 拉取最新代码
systemctl restart web2026     # 秒级重启生效
```

> 若 `requirements.txt` 有改动，重启前补一步：
> ```bash
> source venv/bin/activate && pip install -r requirements.txt
> ```
> 网关路由、systemd 配置无需再动。

### 0.5 回滚

```bash
# 只回滚网关路由（不影响后端）
kubectl delete ingress web2026-route -n higress-system
kubectl delete svc,endpoints web2026-svc -n higress-system

# 停掉后端
systemctl disable --now web2026
```

> 注意：`act-spa-route`、`local-nginx` 及老路由 `/act /tools /cozyAct /qatest2023 /applog` 与本方案完全独立，不受任何影响。

## 三、手动部署步骤

> 如果一键脚本有问题，可以按以下步骤手动操作。

### 3.1 安装系统依赖

**CentOS / RHEL:**
```bash
yum update -y
yum install -y epel-release
yum install -y python3 python3-pip python3-devel nginx gcc
```

**Ubuntu / Debian:**
```bash
apt-get update
apt-get install -y python3 python3-pip python3-venv python3-dev nginx gcc
```

### 3.2 创建 Python 虚拟环境

**方式一：使用 venv（推荐）**
```bash
cd /opt/web2026
python3 -m venv venv
source venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

**方式二：使用 conda**
```bash
# 安装 Miniconda（如未安装）
wget https://repo.anaconda.com/miniconda/Miniconda3-latest-Linux-x86_64.sh
bash Miniconda3-latest-Linux-x86_64.sh

# 创建环境
conda create -n testenv python=3.9 -y
conda activate testenv
pip install -r requirements.txt
```

### 3.3 配置环境变量
```bash
cd /opt/web2026
cp .env.example .env
vim .env
```

修改以下关键配置：
```ini
FLASK_ENV=production
FLASK_DEBUG=False

# 数据库配置（务必修改为实际地址）
DB_HOST=你的数据库IP
DB_PORT=3306
DB_USER=你的数据库用户名
DB_PASSWORD=你的数据库密码
DB_NAME=xianshi
```

### 3.4 创建日志目录
```bash
mkdir -p /opt/web2026/log
```

### 3.5 测试启动
```bash
cd /opt/web2026
source venv/bin/activate   # 或 conda activate testenv
export $(cat .env | xargs)
gunicorn -c gunicorn_config.py app:app
```

验证启动：
```bash
# 检查进程
ps -ef | grep gunicorn

# 检查端口
ss -tlnp | grep 2023

# 测试访问
curl http://127.0.0.1:2023/web2026/
```

### 3.6 配置 Nginx

编辑 Nginx 配置文件：
```bash
vim /etc/nginx/conf.d/http.conf
```

在监听 80 端口的 server 块中添加：
```nginx
# ===== QA测试工具平台 =====
location /web2026/ {
    proxy_pass http://127.0.0.1:2023/web2026/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_connect_timeout 60s;
    proxy_read_timeout 120s;
}
```

检查并重载：
```bash
nginx -t
nginx -s reload
```

### 3.7 配置 Systemd 服务

> 实际在用的服务文件是仓库内的 `deploy/web2026.service`（路径 `/opt/web2026/qa-slpWebTool/webTool`、监听 9090），直接拷贝它比照下文手写更可靠。

创建服务文件：
```bash
vim /etc/systemd/system/web2026.service
```

写入以下内容（注意修改路径）：
```ini
[Unit]
Description=QA Test Tool Platform - Gunicorn
After=network.target

[Service]
Type=notify
User=root
Group=root
WorkingDirectory=/opt/web2026
EnvironmentFile=/opt/web2026/.env
ExecStart=/opt/web2026/venv/bin/gunicorn -c gunicorn_config.py app:app
ExecReload=/bin/kill -s HUP $MAINPID
Restart=on-failure
RestartSec=5
KillMode=mixed
TimeoutStopSec=10
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

启动服务：
```bash
systemctl daemon-reload
systemctl enable web2026    # 开机自启
systemctl start web2026     # 启动服务
systemctl status web2026    # 查看状态
```

## 四、配置说明

### 4.1 需要保持一致的配置项

以下配置项需要互相同步，**务必保持一致**：

| 配置文件 | 配置项 | 默认值 | 说明 |
|---------|--------|--------|------|
| `config.py` | `BASE_PATH` | `/web2026` | 应用基础路径 |
| `deploy/web2026.service` | `-b` | `0.0.0.0:9090` | **实际生效**的监听地址 |
| Higress Endpoints | `web2026-svc` | `192.168.1.27:9090` | 网关转发目标；改端口时需同步 |
| `deploy.sh` | `GUNICORN_PORT` | `9090` | 干净机器一键部署时生成的 unit 端口，已与现网对齐 |
| `gunicorn_config.py` | `bind` | `127.0.0.1:2023` | 仅手动调试用，不参与线上 |
| Nginx（仅自建方案） | `proxy_pass` | `http://127.0.0.1:9090` | 走 Higress 时用不到 |
| `.env` | `DB_HOST` 等 | - | 数据库连接信息 |
| HTML 模板 | `href` 路径 | `/web2026/...` | 页面内链接 |

### 4.2 Gunicorn 配置说明

`gunicorn_config.py` 关键参数：
```python
bind = "127.0.0.1:2023"       # 绑定地址（仅内部访问）
workers = 2                   # 工作进程数（建议 CPU 核数 * 2 + 1）
worker_class = 'gevent'       # 工作模式（协程）
daemon = False                # 不后台化，交给 systemd 托管
loglevel = 'debug'            # 日志级别（生产建议 warning）
```

注意：systemd 单元 `web2026.service` 直接使用命令行参数启动（`-b 0.0.0.0:9090`），本文件仅供手动调试时使用。

单元里额外带了几个稳定性参数：

| 参数 | 作用 |
|------|------|
| `--timeout 30 --graceful-timeout 30` | 单个请求超过 30 秒被回收，重启时给现有请求 30 秒收尾 |
| `--max-requests 2000 --max-requests-jitter 200` | worker 处理约 2000 个请求后自动重启，避免长时间运行内存膨胀 |
| `--access-logfile - --error-logfile -` | 访问日志与错误日志都输出到 stdout，由 journald 统一收集 |

修改本单元后需要 `systemctl daemon-reload && systemctl restart web2026` 才生效。

### 4.3 环境变量与安全开关

`web2026.service` 已配置 `EnvironmentFile=-/opt/web2026/qa-slpWebTool/webTool/.env`（前面的 `-` 表示文件不存在也不影响启动），
所以 `.env` 修改后只需 `systemctl restart web2026` 即可生效；只有修改了 `.service` 文件本身才需要 `systemctl daemon-reload`。

| 变量 | 默认 | 说明 |
|------|------|------|
| `ROOM_CREATE_URL` | `http://127.0.0.1/rpc/Room.Busi/CreateBusiness` | 创建商业房间的 RPC 地址 |
| `SQL_API_TOKEN` | 空 | `/api/sql` 访问口令；**留空则该接口直接关闭（403）** |
| `BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD` | 空 | 平台基础认证，两项都填写才启用；留空则保持现有直接访问方式 |
| `DB_CONNECT_TIMEOUT` | `5` | 建立数据库连接的超时（秒），数据库不可达时快速失败，不卡住 worker |
| `DB_POOL_TIMEOUT` | `10` | 连接池耗尽的等待时间（秒），超时直接报错 |
| `MAX_CONTENT_LENGTH` | `2097152` | 请求体大小上限（字节，默认 2MB），超过返回 413 |

说明：
- `/api/sql` 即使开启口令，也只允许 `SELECT / SHOW / DESC / EXPLAIN` 只读语句。
- 启用 `BASIC_AUTH_*` 后浏览器会弹窗要求输入用户名密码，该口令经网关是明文传输，**仅建议在接入 HTTPS 后开启**。
- 拷贝 `deploy/web2026.service` 到 `/etc/systemd/system/` 之前，先 `cat .env` 核对一遍，避免里面残留的旧配置被带上。
- 作物售价计算器页的「农场作物成熟 / 加工作物成熟 / 钓鱼成熟」已改走 `/api/cropMature`（服务端固定 SQL + 参数化），不再依赖 `/api/sql`，也不需要配 `SQL_API_TOKEN`。
- 写操作（POST）加了轻量跨站防护：请求带了 `Origin`/`Referer` 且与当前站点不同源时直接返回 403；不带来源的 `curl`/脚本调用不受影响。
- 所有响应带上 `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: same-origin`；未引入 CSP，避免影响页面内联脚本。
- 健康检查：`GET /web2026/healthz`（只代表进程存活，不查库）；`GET /web2026/healthz?db=1` 会额外探一次数据库，数据库不可用时返回 503。

## 六、常见问题排查

### Q1: 访问返回 502 Bad Gateway
**原因**: Gunicorn 未启动或端口不对  
**排查**:
```bash
# 1. 检查 gunicorn 是否运行
ps -ef | grep gunicorn

# 2. 检查端口
ss -tlnp | grep 2023

# 3. 查看 gunicorn 错误日志
cat /opt/web2026/log/debug.log
```

### Q2: 访问返回 404 Not Found
**原因**: Nginx 路径配置不匹配  
**排查**:
```bash
# 1. 检查 nginx 配置中的 location 路径
cat /etc/nginx/conf.d/http.conf | grep web2026

# 2. 确认 config.py 中 BASE_PATH 与 nginx location 一致
grep BASE_PATH /opt/web2026/config.py
```

### Q3: 数据库连接失败
**排查**:
```bash
# 1. 测试数据库连通性
mysql -h <数据库IP> -u <用户名> -p -e "SELECT 1"

# 2. 检查 .env 配置
cat /opt/web2026/.env | grep DB_

# 3. 检查防火墙
telnet <数据库IP> 3306
```

### Q4: 页面内链接跳转 404
**原因**: HTML 模板中的 `href` 路径与 `BASE_PATH` 不一致  
**解决**: 确保所有模板中的链接前缀为 `/web2026/`（与 `config.py` 中 `BASE_PATH` 一致）

### Q5: 修改代码后不生效
```bash
# 重启 gunicorn 服务
systemctl restart web2026

# 或杀死后重新启动
kill -9 $(ps -ef | grep gunicorn | grep -v grep | awk '{print $2}')
systemctl start web2026
```

### Q6: update.sh 报 `git pull 失败：本地与远端可能已分叉`
**原因**: 远端历史被重写过（例如修正提交信息时用了 force push），本机旧提交不再是新历史的祖先，`--ff-only` 会直接拒绝。
**解决**: 确认本机无未提交改动后，一次性对齐到远端（只在历史被重写时用）：
```bash
cd /opt/web2026/qa-slpWebTool/webTool
git status                    # 确认无本地改动，有则先备份/暂存
git fetch origin
git reset --hard origin/master
./update.sh                   # 之后照常一键更新
```
> `git reset --hard` 会丢弃已跟踪文件的本地改动，执行前务必看清 `git status`。

### Q7: update.sh 报 `无法访问远端仓库` / `Empty reply from server`
**原因**: 服务器到 GitHub 的网络不通（公司网络限制、未配代理、GitHub 抖动），或 HTTPS 凭据失效。**这与分支分叉无关**，不要 `git reset --hard`。

**先判断**：
```bash
curl -I --max-time 8 https://github.com     # 能否连上
git config --global --get http.proxy        # 是否配了代理
git ls-remote origin 2>&1 | head -3         # 复现 git 的具体报错
```

**方案 A（推荐，服务器不联网也能更新）**：在没有网络限制的本机打包，再把包传上去：
```bash
# 本机（Windows 也可，用 Git Bash / PowerShell 均可）
cd /d/qa-slpWebTool
git bundle create web2026.bundle 4d92e61..master    # 左边填写服务器当前提交（git log -1 --oneline 查看）
scp web2026.bundle root@192.168.1.27:/tmp/

# 服务器
cd /opt/web2026/qa-slpWebTool/webTool
git pull /tmp/web2026.bundle master                 # 从 bundle 拉取，git 状态保持干净
sudo systemctl restart web2026
curl -s http://127.0.0.1:9090/web2026/healthz
```
> 用 bundle 而不是直接覆盖文件，是为了让服务器的 git 记录同步前进，之后网络恢复仍可正常 `./update.sh`。

**方案 B（根治）**：给服务器配代理，或改用能访问的镜像 / 公司内网 GitLab：
```bash
export https_proxy=http://<代理地址>:<端口>
git config --global http.proxy http://<代理地址>:<端口>
```

## 七、回归测试与 CI

仓库自带一套**不依赖真实数据库**的回归测试（stub + 内存 sqlite，会 ATTACH 模拟 `xianshi`/`starship` 跨库前缀），共 112 项断言，覆盖：

- 路由行为：首页/各表单页 200、加钱（含清零口径）、充值成功与失败、建房、公会加入/退出、背包、作物成熟、healthz
- 成长值查表与原逻辑逐值等价
- 校验器边界（uid 位数、金额上限、max 为 0 的情况）

## 八、操作审计

所有**写操作**（POST / PUT / PATCH / DELETE）都会落一条审计记录，GET 页面访问不记录。

| 字段 | 说明 |
|------|------|
| `ts` | 本地时间（ISO8601，带时区） |
| `ip` | 优先取 `X-Forwarded-For` 首段（网关透传的真实 IP）；该头可伪造，仅作参考 |
| `remote` | 直连地址（与网关值交叉验证） |
| `user` | 启用 `BASIC_AUTH_*` 时记录用户名 |
| `action` | 业务动作中文名（加钻石 / 充值 / 作物成熟 / 只读SQL查询 …） |
| `endpoint` / `path` | 路由函数名与原始路径 |
| `uid` | 目标用户 |
| `params` | 白名单字段（uid / money / sql / action …），超长截断，敏感键打码 |
| `status` / `result` | HTTP 状态码 + `ok` / `blocked`(跨站被拦) / `rejected`(4xx) / `failed`(success=false) / `error`(5xx) |
| `ms` | 耗时（毫秒） |
| `ua` | User-Agent（截断 120 字符） |

**落地位置**：`AUDIT_LOG_DIR`（默认 `webTool/logs/`），按天一个文件 `audit-YYYYMMDD.jsonl`，一行一条 JSON。
同时输出一行摘要到 stdout，可以直接跟：
```bash
journalctl -u web2026 -f | grep AUDIT
```

**常用查询**：
```bash
cd /opt/web2026/qa-slpWebTool/webTool

# 今天给哪些 uid 加过钱
grep '"action": "加钻石"' logs/audit-$(date +%Y%m%d).jsonl

# 只看失败的（校验没过/业务失败/被拦/异常）
grep -E '"result": "(rejected|failed|blocked|error)"' logs/audit-*.jsonl

# 按 IP 统计请求数
python3 -c "import json,sys,collections;print(collections.Counter(json.loads(l)['ip'] for l in open(sys.argv[1])))" logs/audit-$(date +%Y%m%d).jsonl
```

**为什么失败能区分开**：页面表单校验不通过时，后端返回的是 **HTTP 400**（页面形态也是 400，
前端只看返回体里的 `success` 字段，不受状态码影响），所以审计里会落 `"result": "rejected"` 而不是 `ok`。
历史上这类失败也返回 200，导致审计把所有失败都记成成功，`edb1572` 之后的版本才修正。

**注意**：
- 审计写失败只打印一行错误，**不会让业务请求失败**（已有用例覆盖）
- 日志目录必须有写权限；若根文件系统只读，用 `AUDIT_LOG_DIR=/var/log/web2026`
- 日志未自动清理，长期跑请配 logrotate，或定期删 30 天前的文件：
  ```bash
  find logs -name 'audit-*.jsonl' -mtime +30 -delete
  ```

## 九、无法出网时发布（粘贴包）

适用场景：**本机能访问 GitHub，服务器不能**，且没有文件上传通道（只能往终端粘文本）。
此时不依赖服务器出网，也不用手工改代码。

### 9.1 本机生成

```bash
cd d:\qa-slpWebTool
python webTool/tools/make_patch.py --from <服务器当前提交>
# 例：python webTool/tools/make_patch.py --from edb1572
```

产出（默认 `dist/`，已被 .gitignore 忽略）：

| 文件 | 用途 |
|------|------|
| `patch-<from>-<to>.sh` | **粘贴用**：内嵌 base64 的 bundle + 全部步骤 |
| `patch-<from>-<to>.bundle` | 原始 bundle，有文件通道时直接传它更省事 |

### 9.2 服务器上粘贴

打开 `dist/patch-<from>-<to>.sh`，**整段复制**到 `192.168.1.27` 的终端回车。
脚本依次做：

1. `base64 -d` 还原 bundle → `sha256sum` 校验（不符立即退出）
2. `git status --porcelain` 检查工作区（脏则提示 `git checkout -- .` 后退出）
3. `git pull <bundle> master`（不访问 GitHub）→ 打印新提交
4. `requirements.txt` 有变更时自动 `pip install`
5. `systemctl restart web2026` → `systemctl is-active` → `healthz` 探活
6. 打印下一步自检命令

任一步失败都会中止，**校验和工作区检查在任何文件被改动之前完成**。

### 9.3 注意

- 仓库路径默认 `/opt/web2026/qa-slpWebTool/webTool`，不同路径用 `TARGET=/your/path bash patch-xxx.sh`
- 服务器必须停在 `--from` 那个提交上（或用 `--from` 指定它当前的提交），否则 bundle 里缺中间提交
- 校验失败常见原因：粘贴时被终端截断/换行、复制时夹带了提示符。重新完整复制一次即可
- 成功后 `git log -1` 即为目标提交；以后再发布重复 9.1、9.2
